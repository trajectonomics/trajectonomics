# The plans page shows every plan side by side, and the switcher manages plans

A person who keeps several plans ("retire at 55", "retire at 60 and buy a condo") needs to give a copy a better name, write down what a plan assumes, mark the one that is their real plan, start a fresh plan from their ledger, and see all of them next to each other before opening one. `traj` can rename a plan, keep notes on it and mark the main plan ([cli ADR 0071](../../../cli/docs/adr/0071-a-plan-can-be-renamed-carry-notes-and-be-marked-main-without-changing-its-document.md)); this ADR is the Dashboard's side of that, #419.

## Decision

- **Three Edits join the closed list of [ADR 0008](0008-the-dashboard-edits-scenarios-through-traj-on-loopback.md), each run dry first and pinned in `edit.test.ts` and `plan-edit.test.ts`.** `rename-plan` is `scenario rename <name> <new-name> --if-hash <hash>`, with the hash the Snapshot's `scenario list` states for that plan, so a rename of a plan changed since is `scenario_changed`. `set-plan-notes` is `scenario notes <name> --file -` with the notes on standard input (never in the argv, so no text can be read as a flag), or `--clear` when the text is empty. The schema holds the CLI's own rules (at most 10,000 characters, no control character but a newline and a tab) so a refusal comes before a spawn; the page sends the text with `\r\n` as `\n` and trimmed. `set-main-plan` is `scenario main <name>`. Notes and the main mark sit outside the document's hash, so neither takes `--if-hash` (cli ADR 0071). Clearing the main mark has no control: the CLI offers it, and the page marks another plan instead.
- **A rename is followed everywhere the server holds the name.** `followPlan` puts the new name where the old one was in the `--scenario` list (an empty list stays empty), and `followCompare` carries it into the comparison the Snapshot's parameters name (and drops the comparison when either of its plans is deleted). Both are applied before the Snapshot is read again, so the next read projects the renamed plan; `plans.test.ts` renames a plan against the workspace `traj` and reads both lists. The page then moves the address bar's `scenario` to the new name when the renamed plan was the one shown.
- **A new plan is `apply-plan` with a template, or `copy-plan`.** "A copy of <plan>" is the `copy-plan` of ADR 0008, unchanged. "From my accounts today" is an `apply-plan` that carries `{ template: { asOf } }` in place of a document (the Snapshot's As-of, which the page never computes). The server reads the template (`scenario apply --template --as-of <date>`, [cli ADR 0044](../../../cli/docs/adr/0044-a-template-can-be-pre-filled-from-the-baseline.md); the page cannot, since only the server runs `traj`) and applies it under the name with `--file -`: the template prints minor units, so it takes no `--decimal`. This shape names no `--if-hash`, because the plan does not exist yet, and `scenario apply` under a taken name would replace that plan's document. So the dry run's `status` must be `created`: anything else answers `scenario_name_taken` and the real write never runs (`scripts/plans.test.ts` applies over a plan that has notes and checks it is untouched). A window of milliseconds remains between the dry run and the real write: a plan of that name made by a terminal in it would be replaced. The real write's own `status` is checked too, and when it is not `created` the answer says the plan was made while this ran and was replaced; the write cannot be undone, so it is reported, not prevented. The schema is a union of the saved shape and the template shape, because Zod's discriminated union takes one option for each kind; the template shape is strict and carries nothing else.
- **A plan outside the dashboard is added by a reread, not a write.** `POST /reread` takes `{ "addPlan": "<name>" }`, sent alone: a body that adds `allowances` or `chance` to it is refused, because those rereads would skip the added plan (`plan-edit.test.ts`). The server adds the name to the `--scenario` list when the list is explicit and the ledger holds the plan (the held `scenario list` read), and reads the Snapshot again. It writes nothing. A name the ledger does not hold is passed over.
- **The main plan is first, and it is what the pages open on.** `planStageTwo` puts the ledger's main plan first in the plans it projects (in an explicit list too), the rest in the order they had. Every page, Home included, shows the plan the address bar names when it is one of those plans, and otherwise the first one (`chooseScenario` in `src/lib/view/plan.ts`, the one rule, #268). Home used to ignore the address bar and to prefer a comparison's plan; neither now decides it. The choice reads the Snapshot's list and never an object's keys, whose order JavaScript changes for integer-like names.
- **`/plans/` is one card for each projected plan**, the main plan first and then in the order `scenario list` states (by name; manual order is cosmetic and left out). A card has the name, a "Main" tag, the notes' first line (the whole text opens under it), the FI month and the ages on it from the `fi` read, the chance of success when the Snapshot holds that read, net worth at the end of the run from the projection, and a net worth line chart of the annual rows with a rule for each Milestone reached. It links to that plan's Overview (`/projection/?scenario=<name>`). Every figure is the CLI's own string, shown as it stands ([ADR 0002](0002-the-cli-is-the-only-source-of-figures.md)); the page adds no money and no date.
- **The range control filters rows and computes nothing.** "Next 10, 20 or 30 years" and "Whole plan" are `?range=10|20|30|all`. A range draws the first N rows of the plan's annual table, as the CLI wrote them, and a Milestone that no drawn row holds has no rule (`dayPosition` returns null). No date is added to the As-of: the first annual row may be a partial year, so N rows can span a little less than N years, and the words say "years" as the CLI's annual table counts them. The figures on a card do not follow the range; only the charts do.
- **Plans the dashboard does not project are listed by name** from `scenario list`, with "Not projected in this dashboard", and an action ("Add <name> to this dashboard") when Edits show. They have no card: nothing was read for them.
- **One menu, one drawer.** The plan switcher is a list of the plans the pages can show, each with its name, a "Main" tag, a notes icon and, when Edits show, a menu: Rename, Notes, Make this my main plan (not on the main plan), Copy plan, Delete plan. A "New plan" action and a "See every plan" link follow the list. The `/plans/` cards carry the same menu (`PlanMenu`). Rename, notes, copy, new and delete open one drawer (`PlanDrawer`, mounted once in the layout, state in `src/client/plan-editor.svelte.ts`), so both menus open the same form; "Make this my main plan" runs at once. Deleting the main plan says to choose another first and offers no delete, since `traj` refuses it (`scenario_is_main`), which `plans.test.ts` also pins. The controls show only when the server answers the token, as the other Edit controls do, and never in the Demo snapshot. The Demo snapshot and its generator are not touched here.

## Considered Options

- **A fourth Edit kind for a new plan from the accounts.** Rejected: the issue states it as an `apply-plan`, and a template is the document that Edit applies. The cost is the union in `editSchema` and a server read before the write.
- **Compute the range from the As-of (As-of plus N years).** Rejected: it adds to a date in the page. Choosing rows the CLI already wrote needs no calendar.
- **Show every plan on `/plans/`, projected or not.** Rejected: a card of figures needs reads, and a plan with none would show a blank card. Reading every plan on every Snapshot would make every Edit slower for a plan nobody opened; adding one is a single reread.
- **A select for the switcher.** Rejected: an option cannot carry a tag, an icon or a menu, and a menu on a select is a second control beside it.
- **Make the main plan the default of every read.** Not done; cli ADR 0071 keeps a label only. The pages open on it because the Snapshot lists it first, which is the Dashboard's own choice.

## Consequences

- Every new Edit kind stays a change to `src/lib/edit/edit.ts`, its pinned list and ADR 0008's list, which this ADR amends: the list now also holds `rename-plan`, `set-plan-notes` and `set-main-plan`, and `apply-plan` may carry a template.
- A Snapshot saved before cli ADR 0071 has no `main` or `hasNotes`; it reads as no main plan and no notes, so the pages open on their first plan as they did.
- The Demo snapshot has no main plan and no notes, so `/plans/` there shows two cards, the notes empty and no menu.
