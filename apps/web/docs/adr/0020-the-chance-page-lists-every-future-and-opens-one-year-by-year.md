# The Chance page lists every future and opens one year by year

"18 per cent of futures run out" is hard to trust until a person has seen one of those futures. `traj projection chance --outcomes` states what each seeded Market path came to, and `traj projection path --index N` replays one exactly ([cli ADR 0069](../../../cli/docs/adr/0069-a-market-path-is-named-by-its-index-under-a-seed-and-projection-path-replays-it.md)). The Chance page lists every future in a table, offers the CLI's five picks as cards, and opens a future on its own page, year by year. Every figure is the CLI's decimal string ([ADR 0002](0002-the-cli-is-the-only-source-of-figures.md)); the page orders and filters them and adds none.

## Decision

- **One read, not two.** The Snapshot's `projection chance` takes `--outcomes` unless the parameters say `futures: false` (`PlanParams.futures`, true by default; only the Demo's input says false). `outcomes` is one row per path in path order; `representative` holds the indexes of the 10th, 50th and 90th percentile paths, the earliest run-out (null when none ran out) and the deepest fall. The contract (`projection-chance.ts`, `projection-path.ts`) already decoded both; no decode gap came up.
- **The Snapshot pre-reads the five representative paths of each plan.** `reads.paths[plan][index]` is a `projection path` read (the same flags as the chance read plus `--index=<n>`, one token each, the plan's Carry-in on standard input), for each distinct representative index, `default({})` for an older Snapshot. They are planned after the chance read, because the indexes are in its answer (`representativeIndexes`, `StageTwoPlan.pathOf`), and run one at a time (`scripts/run-paths.ts`). `projection path` joins the read-leaf allowlist (`leaves.test.ts`).
- **Any other index is read live through `POST /reread`**, as a new key of its strict body: `{ "path": { "plan": "<name>", "index": <n> } }`, alone (a body that adds `allowances` or `chance` is refused). It sits behind every guard of [ADR 0008](0008-the-dashboard-edits-scenarios-through-traj-on-loopback.md), [0010](0010-the-what-if-session-reads-through-traj-on-loopback.md) and [0012](0012-the-tax-allowances-page-reads-what-traj-says-each-allowance-could-take.md): Host, Origin, the token, `application/json`, the 1 MiB cap, the depth cap and one request at a time (a path read and an Edit share the busy flag). The plan name passes the Edit's name rules (never a leading `-`, no control character, 100 characters), the index is an integer from 0 to 9,999, and the server refuses (400, `invalid_path_index`) an index at or above the run's `paths`, a plan the Snapshot does not hold (`unknown_plan`), or a Dashboard with no chance inputs (`no_chance`). It runs that one argv (`pathRead`, always a `projection path`) and answers `{ ok: true, path: <the Read> }` (the CLI's own refusal is that Read's error, as data). **It changes nothing else:** the held Snapshot, the served body and the parameters are untouched, and nothing is written. The page keeps the answer in the tab (`src/client/path-reads.svelte.ts`), tagged with the run it was read for.
- **A replay always belongs to the chance on screen.** `sameRun` compares the path's `definition` (model id, seed, paths), its plan's `scenario.effectiveContentHash` (which a terminal edit changes) and its dates with the chance read's. The server checks it against the chance it holds before it answers, and answers `path_of_another_run` instead of a path that does not match; the page checks it again before it draws (stored or live), so a Snapshot that moved on, a live read made before a paths-or-seed reread, or a tab left open over a plan edited in a terminal shows "different run" and never another future. A live read is reused only for the run (`runKey`) it was read for.
- **A paths-or-seed reread reads the paths again.** The chance inputs change which paths are representative, so `POST /reread { chance }` ([ADR 0018](0018-the-assumptions-page-sets-inflation-each-accounts-return-and-swing-and-the-chance-of-success.md)) runs the chance reads and then the path reads of the new picks, under the same staleness check; `stillCurrent` counts the path reads among the reads it runs again, and `withChance` swaps chance and paths together. On a scratch ledger of one plan the chance change took 3.0 to 3.6 s (1.5 s before: five more reads), still against a full read of 10 s (`scripts/assumptions-reread.test.ts`).
- **Sorting is by string.** The CLI's JSON states no order (path order, which is what `--index` counts in); its human table lists worst closing net worth first, a tie to the lower index. The page does the same, and can also list the best first. `compareMoney` (`src/lib/view/chance/order.ts`) orders two decimal strings by sign, then the length of their whole digits, then the digits, then the fraction padded with zeros; no number is made of a string, so a figure past 2^53 still orders exactly. "Only the ones that ran out" keeps the rows whose `runsOut` is not null; the count and the page (25 rows) come from the list's length. The only conversion is `toChartNumber`, for the bar's width (a share of the longest bar, a mark never shown as a figure); a bar below zero is the destructive colour, and the minus sign shows in the figure beside it.
- **The words.** "Lowest point" is `lowestNetWorth`, with "in the year from Oct 2051": `lowestYear` is the first day of the roll-up the path was lowest in (cli ADR 0069), and a roll-up need not start in January, so the page says the month it starts in and does not call it a calendar year. "Ran out in Jun 2052" is `runsOut.date` as a month, "Lasted" is no run-out. Paths are numbered from 0, as `--index` numbers them ("Future 0 of 200" to "Future 199 of 200").
- **The five cards** are `representative`, in the issue's words: "A bad future (10th percentile)", "A typical future", "A good future", "The earliest run-out" (left out when no path ran out) and "The deepest fall". Each shows how it ended, its closing net worth and its lowest point, and links to its future.
- **The path page** is `/chance/path/?scenario=<plan>&index=<n>`, a page opened from the Chance page and not in the navigation (the side navigation marks Chance of success as the current page, `navPath`). Every link keeps the rest of the query (`demo`, `terms`). Its header is "Future <n> of <paths>", how it ended (the run-out month and the shortfall the CLI states, or "Lasted to <horizon>"), the closing net worth and lowest point from the chance's `outcomes` when the Snapshot lists them, and the way back. Net worth by year is a bar chart (`LineChart`, `kind="bars"`) with the reached Milestones as the Projection page draws them and a "Ran out" rule on the run-out date, each placed inside the bar of its roll-up (`columnLayout` takes markers, placed by `dayPosition` within the column of the period); the nominal/real switch is the Projection page's (`terms` in the query), always available because every annual row states `realNetWorth`. The table has a row per year: the month it ends in, the household's ages, each model Account's return (`returns`, matched to the year by roll-up index, named from the accounts read), income, spending (`expense`) and net worth, with a "Lowest point" and a "Ran out" badge on their years. A sentence says each return is the market's growth from the year's first day through its last, so it covers one day more than the closing net worth and is free of what was paid in or out (sim ADR 0011).
- **The Demo snapshot does not grow.** It is at 1,040,886 bytes of Biome's 1,048,576-byte limit (99.3%; #378 waits on the owner), 7,690 bytes free. The 200 outcomes of one plan alone would add about 30 KB before indentation and about 40 KB as the formatter writes it, and each path read about 40 KB, so neither fits, even for one plan. The Demo is not rebuilt: its chance read has no `outcomes`, and `reads.paths` is absent and reads as `{}`. `scripts/demo-run.ts` states `futures: false`, so `bun run demo` still makes a file of the same size (it would add the key `"paths": {}`, 14 bytes). On a Snapshot with no `outcomes` the Chance page shows what it did before and says that a live dashboard (`traj dashboard`) lists every future and opens each year by year; a path page with no stored read and no live dashboard says that a live dashboard can open it.

## Considered Options

- **A second read for the outcomes.** Rejected: the issue asks for the existing chance read with `--outcomes`, and a second read would run the chance twice.
- **Pre-read every path.** Rejected: 10,000 reads of 30 KB each. The five picks are the telling ones; any other index is one live read.
- **Put a live path into the Snapshot the server holds.** Rejected: a later partial reread would have to keep or drop it, and "a path read leaves the rest alone" is simpler to state and to test.
- **Sort on numbers.** Rejected by ADR 0002: a number can lose digits. A comparison of strings cannot.
- **A calendar year for the lowest point.** Rejected: the CLI states the first day of the roll-up, not a calendar year, and a plan whose As-of is in October has roll-ups from October.

## Consequences

- `scripts/futures.test.ts` runs against the workspace `traj`: the Snapshot lists every path and holds exactly the representative ones, each of the chance's own run, and a path's closing net worth and run-out equal the chance's outcome for that index; the earliest run-out opens from the Snapshot with its fall year and its run-out marker; a non-representative path is read through `POST /reread` and the served Snapshot is byte for byte what it was; a plan or index the server cannot name, a body with another field, a wrong token, Origin, Host and content type are refused; a chance of another run answers `path_of_another_run`.
- `scripts/assumptions-reread.test.ts` also pins that a paths-or-seed reread reads at most five paths again, all of the new run.
- A `traj` without `projection path` (before 0.8.0) answers each path read as an error, and the Chance page then lists no futures because its read is refused for `--outcomes` as an unknown flag, which the page shows as the read's own error.
