# The hosted Demo is a second build target with no edit client

[ADR 0009](0009-the-demo-dashboard-is-hosted-on-the-site.md) decided to host the Demo on the Site and left the build to the change that ships it ([#342](https://github.com/trajectonomics/trajectonomics/issues/342)). This is that build, in `apps/web`. The Site copies its output in a separate change.

## Decision

- **A second build, chosen by one environment variable at build time.** `bun run build:hosted` is `TRAJ_WEB_TARGET=hosted vite build`. `vite.config.ts` reads the variable once. Only then does it add the twin plugin (`hostedTwins()`), set the base path and move the output; the JSON that holds them (`src/hosted/overrides.json`) is always imported, and without the variable nothing in it is used, so the config builds the loopback build. The variable is not read at run time, and nothing in the shipped pages can switch target.
- **Its own folders.** The pages go to `dist-hosted/` (never inside `dist/`, so `scripts/pack.ts` cannot pack them into `dashboard.bin`) and SvelteKit's working folder is `.svelte-kit-<name of the output folder>/` (`.svelte-kit-hosted/`, or another one when `TRAJ_WEB_OUT` moves the output, so two builds never share a working folder). Turborepo has a `build:hosted` task whose output is `dist-hosted/**`. `TRAJ_WEB_OUT` moves the output, for the test that builds it into a scratch folder.
- **The base path is `/demo`.** `src/hosted/overrides.json` holds it (`base`), and both SvelteKit's `paths.base` (in `vite.config.ts`) and every link the hosted twins write start from that one value. The prerendered pages, their links and `_app/` assets are all under `/demo/`. The Demo snapshot is `public/demo/snapshot.json` as before, so it is served at `/demo/demo/snapshot.json`.
- **The hosted build is the loopback build's sources with a closed list of modules swapped.** `src/hosted/overrides.json` (`modules`) maps a module under `src/` to its twin in `src/hosted/`, and `hostedTwins()` in `vite.config.ts` (a Vite plugin, in the hosted build only) resolves each import as Vite would and answers the twin when the file is on the list. A twin may import the module it stands in for (the layout twin renders the layout). No page, component or module of the loopback build is edited for the hosted target, so the loopback build is the same files as before except SvelteKit's build stamp (`_app/version.json` and the pages that name it), which `scripts/pack-fingerprint.ts` masks (the pull request records the `sha256` of `dashboard.bin` and its fingerprint before and after). The twins:
  - **Where the pages are and what they read.** `snapshot-url` (`isDemo` is always true and `snapshotUrl` always answers the Demo snapshot under the base path, whatever the query string says), `links`, `chance-links` (each link goes under the base path) and `routes` (the navigation finds the page with or without it).
  - **No write path.** `shown` (`editsShown` is true: the Edit controls are drawn), `edit-session`, `edit-post`, `reread`, `what-if-remote` and `path-reads` (every request the loopback client sends is a twin that sends nothing and answers that it could not), and `path-state` (a future the Demo snapshot did not read is never read live).
  - **The shell.** `layout` renders the loopback layout with the notice above each page and the fence around everything.
- **The loopback build is shown unchanged by a fingerprint.** SvelteKit stamps every build with the time it ran, so `dashboard.bin` is never the same file twice, even for one commit. `bun scripts/pack-fingerprint.ts pack/dashboard.bin` hashes every file of the Pack with that stamp replaced, so it is equal for two builds of one source and changes when a file does. The pull request records the `sha256` of `dashboard.bin` and its fingerprint before and after. Tailwind scans all of `src/`, so code that only the hosted build imports must not add a utility class to the stylesheet either: it uses a class the loopback pages already have, or an inline `style` (as `HostedNotice` and the fence do). A class that is new shows in the fingerprint.
- **The edit controls stay, switched off.** The pages draw them, because `editsShown` is true, and one component, `HostedFence`, switches them off for every page: a MutationObserver in `src/client/hosted-fence.ts` (it watches added nodes and the `disabled` and `draggable` attributes, and its own writes are made only when they change something, so it settles) disables each button, field and select in the page and the plan switcher except a short list of controls that only choose what the page shows or only touch the visitor's own browser (the scenario, terms and range choices, the year, account, table and chart pickers, the estate date, the ledger filter, the toggles that carry `aria-pressed` outside a form or `aria-expanded`, and a saved chart's Edit, Duplicate and Delete, Export and Import, which keep charts in `localStorage` and send nothing; an `aria-pressed` toggle inside an Edit form fills a switched-off field, so it is switched off with it), and sets each one's `title` to say what it would do and where: "Add account: switched off in this demo. Install traj and run traj dashboard to do this to your own plan." A control the fence does not know is switched off, not left on, so a control added later is safe by default. The title of a field is the label that names it, never the options of a select. The `Actions` menu of a plan still opens, and carries the same title as the items it holds. A dialog is left alone, because only a switched-off control opens one, except the charts' own drawer, which keeps a person's charts in their own browser. `HostedNotice` says once at the top of each page that the numbers are made up.
- **How "no Edit" is enforced, in code and not by convention.**
  1. The hosted build has no edit client: the six twins above contain no `fetch`, no `XMLHttpRequest`, no `sendBeacon`, no WebSocket and no name of the write path, and `src/hosted/overrides.test.ts` fails if one does.
  2. `overrides.test.ts` also fails when a file outside the list calls the network or names the write path (every string export of `src/lib/edit/guard.ts` that ends in `_PATH`, and `EDIT_TOKEN_HEADER`, read from the module, so a path added there is covered). The one file that may call the network without a twin is `src/client/browser.ts`, which reads a Snapshot from the path `snapshotUrl` gives it, and the test pins that it holds exactly one `fetch(`. A new client for a new Edit therefore fails the test until it has a twin.
  3. `scripts/hosted-build.test.ts` builds the hosted target and reads the output: it holds no `*.json` but the Demo snapshot, none of the write path's paths (the same list), no token header, no `method: "POST"` and no `method=post` form, and a positive control shows the scan reports every name on the loopback build's `dist/`; every root-relative link and asset of every page is under `/demo/`.
  4. `browser/hosted.e2e.ts` serves `dist-hosted/` under `/demo/` (anything else is a 404) and, for every route at 360px and 1280px, reads Playwright's request log: every request is a GET of this origin under `/demo/`, the only Snapshot read is the Demo snapshot, every control that is switched off says `traj dashboard`, a click on every control still on sends nothing, no response under `/demo/` has a status of 400 or more, and, with one chart seeded into `localStorage`, every control that is on in the loopback Demo (`?demo=1`) is on in the hosted build too.

## Considered Options

- **A flag in the pages (`if (hosted)` in each component).** Rejected: every page would carry two behaviours, the loopback bundle would change with each edit, and a missed branch would be an Edit that reaches a server that is not there. A closed list of twins is one place to read and one test to fail.
- **Hide the Edit controls, as `?demo=1` does on loopback.** Rejected: the visitor would not see that the Dashboard can change a plan, which is what the install is for.
- **Set `disabled` in each component.** Rejected: about forty components would each need the two states and the sentence. One fence applies to all of them, and `overrides.test.ts` and the browser check keep it honest.
- **`paths.relative` instead of a base path.** Rejected: only assets become relative. The pages' own links are root-relative and would point outside `/demo/`.

## Consequences

- The Site's change builds `build:hosted` (`bunx turbo run @trajectonomics/web#build:hosted`), copies `apps/web/dist-hosted/` to `/demo/` of the Site and links "Try the demo". Nothing under `apps/web` is deployed on its own, and no Worker, route or credential is added here ([ADR 0004](0004-no-server-and-no-hosting.md), [ADR 0009](0009-the-demo-dashboard-is-hosted-on-the-site.md)).
- A visitor on a keyboard or a touch screen never sees a `title`, so for them only the notice at the top of each page explains a switched-off control. The `title` is a help for a pointer, not the explanation.
- A module that gains a network call needs a twin first. A page that gains a control that only reads must be added to the fence's list, or it is switched off.
- Charts a visitor saves are kept in the browser under the `/demo/` origin path, and their series ids embed account ids that the Demo snapshot generates anew on every build ([#477](https://github.com/trajectonomics/trajectonomics/issues/477)). Until the Demo's ids repeat, a deploy drops a visitor's saved charts.
- The first-run empty state is unchanged: the hosted build always has a Demo snapshot, so it never shows it ([#324](https://github.com/trajectonomics/trajectonomics/issues/324)).
