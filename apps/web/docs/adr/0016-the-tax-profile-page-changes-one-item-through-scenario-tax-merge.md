# The Tax profile page changes one item through `scenario tax --merge`

A person who wants a second child counted should not have to state the whole tax profile again. `traj` keeps the profile a plan was taxed with beside the plan and changes one item of it ([cli ADR 0066](../../../cli/docs/adr/0066-scenario-tax-keeps-the-profile-it-was-given-beside-the-scenario.md)). The page, in a new Settings group, shows that profile and sends the change. Every figure is the CLI's ([ADR 0002](0002-the-cli-is-the-only-source-of-figures.md)); what the page shows is the person's own input, and no allowance, limit or rate is named in it.

## Decision

- **Read.** No new read. `scenario show` of each plan, already in the Snapshot, carries `tax` (the stored profile or null) and `taxed` (the document holds a Levy). A Snapshot saved before them states neither, so `tax` reads as null and `taxed` reads from the document's Levies. The Demo is unchanged: it has no profile, so it shows the plan as taxed with no stored profile and no controls.
- **The page.** `/settings/tax/`, "Tax profile" in a "Settings" group after Records, listed when the plan has a document. The title is not "Tax", which the report page already is. It says the tax is Thai personal income tax for the 2026 tax year, that a contribution to an SSF is not deductible from 2025, that the Flows taxed are the ones that carry a tax label and that this page does not change those labels. A plan with no profile and no Levy shows nothing filled in; one with a Levy and no stored profile (taxed before profiles were kept, or its tax rules changed by hand since) says so.
- **Three Edits** (`merge-tax`, `set-tax`, `remove-tax`), each one `scenario tax` write that names the hash the page read ([ADR 0008](0008-the-dashboard-edits-scenarios-through-traj-on-loopback.md)), run dry first like every Edit:
  - `merge-tax` is `scenario tax <name> --merge <flags> --if-hash <hash>`. The form sends only the items whose text differs from the stored one; an amount emptied is sent as `0`, which takes it out; a count of children cannot be emptied. It needs at least one flag, and the schema refuses an empty merge.
  - `set-tax` is `scenario tax <name> --tax th-2026 <flags> --if-hash <hash>`, the whole profile. The filing status is chosen, never assumed: the form starts with it unchosen and the schema requires it. An item left empty is none, and the form says anything an earlier write stated and the person leaves out is dropped.
  - `remove-tax` is `scenario tax <name> --none --if-hash <hash>`, not `--remove`, after a confirmation that says the tax rules, the stored profile and the tax labels on the Flows go with it.
- **Values are text shaped for `traj`.** The Edit carries each count as whole digits and each amount as digits with at most two decimals, so no value can be read as a flag. `traj` parses and range-checks every one, and the page does no arithmetic (`src/lib/edit/tax-flags.ts`, pinned in `tax-edit.test.ts`).
- **Merge or whole.** A stored profile is changed one item at a time, and the form can switch to stating the whole profile, which clears it. A plan with no stored profile goes straight to the whole form, because `--merge` would refuse. A merge the CLI still refuses for want of a profile (its path is `--merge`) shows its message and a "Set the whole profile" action.
- **Refusals** land at their field in the CLI's own words. `scenario tax` names the flag in its path (`--children-at-higher-rate`), which maps to the form field of the same name; a `--merge` of fewer children than the stored higher-rate count is therefore refused at the higher-rate field, because the CLI checks the merged profile. A path that names no field (`--tax`, `--if-hash`) is shown for the whole form. A stale page is refused as `scenario_changed`, with "This plan changed since the page read it." and Reload.
- **A plan moves under the form.** The form is made again whenever the plan's hash changes, from the profile stored then, and says so ("the plan changed since you opened this form"); a Reload therefore never carries an old value over an item someone else changed, and a profile that is no longer stored gives the whole form with nothing in it. A merge also sends only the items that differ from the profile the form opened with, so an item changed elsewhere is never rewritten by a save that did not touch it.
- **Income Flows with no tax label.** (Superseded by the amendment below: the page now sets labels.) `scenario tax` refuses a plan while an income Flow has no tax label, and `--none` clears every label, so a plan with such a Flow (an untaxed plan with any income Flow, or a plan such as the Demo's `base`) cannot be set or merged from this page, which does not set labels. The page then names those Flows and the command that labels them (`traj scenario tax <name> --merge --label <flow>=<label>` with a stored profile, `--tax th-2026 --label <flow>=<label>` without) instead of offering the form. A label counts as set when `traj` knows it (see the amendment below). The Remove confirmation says that putting tax back needs that command, and a `document` refusal that lists Flows is shown as a sentence naming them. Removing tax stays available.
- **The controls** appear only when the server answers the token, and never in the Demo snapshot, as every Edit control does. `followPlan` leaves the plan list as it was.

## Considered Options

- **A merge for every change, whole only for a first write.** Rejected: a plan taxed before profiles were kept, or one whose tax rules were changed by hand, has no stored profile, and its merge is refused. The page offers the whole form there instead of failing.
- **Sending the whole profile for every change.** Rejected: the page would restate items it did not change, and `--merge` exists to avoid exactly that.
- **A default filing status of `single`.** Rejected, as no share, rate or relation is defaulted elsewhere in the page: the person chooses.
- **Adding a Tax profile read to the Snapshot.** Rejected: `scenario show` has it, and the Demo is at 99.3% of Biome's 1 MiB limit.

## Consequences

- A change in the CLI's output fails `src/lib/contract/` and `scripts/contract.test.ts` as before; the Edits' argv is pinned in `src/lib/edit/tax-edit.test.ts`.
- `scripts/tax-settings.test.ts` runs a whole set, a merge that keeps the other items, a deduction stated as zero, a merged-profile refusal at its field, `--none` followed by a merge refused with the whole form named, and a stale save, all against the real binary; `scripts/tax-labels.test.ts` adds a save from a form opened before someone else's change (kept after a Reload), a plan with an unlabelled income Flow (the refusal names the Flow), and the label command followed by a merge and a Remove.
- A `traj` older than `scenario tax --merge` refuses the flag; the CLI the Dashboard ships with has it.

## Amendment (2026-11-24): grouped cards, what is not in the plan yet, tax per year and tax labels

The page showed one list of rows with one drawer. It now shows the stored profile as cards, and #436 added the rest.

- **Group cards.** The stored profile is six cards: filing status, family (children, children born 2018 or later, parents, disabled care), insurance (life, health, parents' health, spouse's life), home (home-loan interest), giving (the two donation items) and social security. Each has an Edit that opens the drawer on that group's items only; a refusal that names an item of another group (a merge is checked against the merged profile) is shown for the whole form. "State the whole profile instead" still shows every item. The grouping is `GROUPS` and `PLACE` in `src/lib/view/tax-settings/groups.ts`. `PLACE` is a `Record` over `TAX_CLASSES`, the class list of `scenario tax`, so a new class fails the typecheck, and `scripts/tax-cards.test.ts` fails when `traj` reports a class the list lacks. The cards are shown only when a profile is stored; a plan with none keeps the sentence and the "Set the tax profile" button.
- **Not in your plan yet.** Under the cards, the classes `scenario tax` reports in `notStated`, each opening the drawer on its group. No new read: `notStated` was worked out in `not-stated.ts` from the stored profile and the plan's contribution Flows (superseded below). The two retirement classes are not flags, so they link to the Tax allowances page instead of the drawer. The page worked the list out itself; the amendment of 2026-11-25 below moves it to a `traj` read.
- **Tax per year.** Under the cards, the tax years of the plan's `projection run` read the Snapshot already holds: the period, when it settles, the due and owed figures in `traj`'s text, and a Refund mark for a negative owed. The page does no arithmetic. After a save the Snapshot is read again, so the table shows the effect of a change; `scripts/tax-cards.test.ts` adds a child with a merge and sees the owed figures change.
- **Inside a What-if session.** While a What-if session of the plan holds a change, every control that writes tax (the card Edits, the not-stated buttons, Set, Remove and the label form) is disabled, with "Tax settings are saved, not tried." A session of another plan changes nothing here. The drawer is shut while the session is open.
- **Tax labels.** `traj` writes a label only beside a Levy: `scenario apply` refuses a label on a plan with none (`LEVY_REQUIRED`), and `scenario tax --label` needs `--tax`. So there are two paths, and the page picks by whether the plan is taxed. A taxed plan with an income Flow that has no label (a Flow added later) shows a Tax labels form, which chooses a Flow and one of the 22 income labels `traj` lists and saves an `apply-plan` Edit that names the hash the page read; the stored profile stays, because the Levy is unchanged. A plan with no tax labels its Flows in the write that gives it tax: the whole-profile form asks for a label for each, and `set-tax` carries them as `labels` (`--label <flow>=<label>`, see [ADR 0008](0008-the-dashboard-edits-scenarios-through-traj-on-loopback.md)). While a taxed plan has unlabelled income the card Edits are not offered, as `--merge` refuses it. A refusal of a label lands at its field in the Tax labels form of a taxed plan; in the whole write it shows at the form level. "Has a tax label" means what it means in `traj`: an income Flow whose label `traj` does not know (such as `income.section40_9`) counts as having none, so the label form offers it and its save replaces the label. A `document` refusal that names Flows is told apart by `details.labels`: income labels send the person to the Tax labels form, and contribution labels (a contribution Flow whose label the Levy does not read) name the Flows and say the label is edited from the Income page's contribution form, because the Tax labels form lists income Flows only. `apply` does not check the label's name on a taxed plan, so the form offers only the list and the Edit schema is closed over it; `scripts/tax-cards.test.ts` reads the list from `traj scenario tax --help`.

## Amendment (2026-11-25): the not-stated list is `scenario show`'s `taxAllowances`

The page no longer works out which classes the plan leaves out. `scenario show` now reports `taxAllowances: { stated, notStated }` for a taxed plan with a stored profile ([cli ADR 0073](../../../cli/docs/adr/0073-scenario-show-states-which-tax-allowances-the-plan-states-and-which-it-does-not.md)), from the function `scenario tax` reports `allowances` with, and it is already in the Snapshot, so this adds no read. The contract decodes it as optional (class names are kept as strings, so a class a later `traj` adds still decodes); `notStated` in `src/lib/view/tax-settings/not-stated.ts` only gives each class its words and its place (`PLACE`), and a class it has no place for is listed by name without a button. A plan with no `taxAllowances` (an older Snapshot, or the Demo, which stores no profile) lists nothing. The page's behaviour is otherwise as before.

`scripts/tax-cards.test.ts` and `scripts/tax-label-cases.test.ts` still compare against `scenario tax --from-stored --dry-run`: the show's `taxAllowances` equals its `allowances`, and the page's list is that `notStated`, for plans with no contribution Flow, an RMF one, a ThaiESG one, or both. `tax-not-stated.svelte.test.ts` pins that the page lists exactly the classes it is given.

## Amendment (2026-11-26): the shared home-loan interest, and card labels after a holder swap

- **The field.** The stored `sharedMortgageInterest` ([cli ADR 0075](../../../cli/docs/adr/0075-a-two-earner-plan-states-its-filing-choice-and-scenario-tax-writes-one-levy-per-return.md)) is shown in the Home card, and the form sets and clears it as `--mortgage-interest shared=<amount>`: an emptied or all-zero field sends `shared=0`, which removes it. The field is offered whenever the draft files separately and the household names a partner and Owners, which is what `traj` reads `shared=` for; it reads that from `scenario show`'s household, never from the projection, so a plan whose projection is refused (a mid-year start with no carry-in) and a plan still to be taxed both offer it.
- **A whole save fills it in.** The whole-profile form pre-fills a stored value whenever the household can claim one, whatever the profile's stored status, so a plan that kept a value under a joint filing and is saved whole as separate keeps it. The sentence that says an item left out is dropped is followed by one that says the shared interest is filled in, and that one is shown only while the draft files separately, when the field is offered. When the person clears it, or types an all-zero amount, the form says "This save drops the stored shared home-loan interest of N THB." before saving. A whole save with no partner or Owners fills nothing and shows that sentence.
- **The Home card.** On a separate filing it shows the shared row; where no Return claims the stored value (a status that is not separate, or a document whose Levies name no Filer, such as `th-2026-pit` rather than `th-2026-pit@<filer>`) the row says it is kept and not claimed by this Return, and under another status with no stored value the row is absent.
- **Holder swaps.** Only a separate write moves `claimsHolder`, and another status's flat keys are that Return's own claims, so the cards say "you" there. On a separate filing whose recorded holder is not the household's holder the cards name that person ("Parents your partner supports"); an id the household no longer names is called "The earlier holder", never the id, and a page with no household holder says "you".
- **Refusals.** A `--mortgage-interest` refusal lands at the shared field when the save sent only `shared=`, or when the CLI's sentence says `shared=`, even if the sentence does not name it (an amount outside its allowed range); it lands at the person's own field when only a bare interest was sent. When both were sent and the sentence says neither, no field can be told and the form shows it whole. `scripts/tax-settings.test.ts` runs the real `traj` for both cases, so rewording its sentence breaks the test.

## Amendment (2026-11-26): the CLI's notes about the stored claims

`scenario show` carries the stored profile, but the CLI's own notes about the claims it keeps reach only a `scenario tax` write result, never a projection's `taxYears`. The Snapshot therefore gains one `scenario tax <plan> --from-stored --dry-run --json` read per plan with a stored profile, the only read the Plan emits with `--dry-run`: it rolls the write back, so it stores nothing. A dry run takes the ledger's writer lock, so it can answer `database_busy` while the person runs `traj` writes, and that is retryable (cli ADR 0019). `src/lib/contract/scenario-tax.ts` validates the write result, and `src/lib/view/tax-settings/notes.ts` keeps only the CLI's sentences: the `unclaimed` list, and the separate-loans sentence the CLI appends to tax-core's own note on `allowances.mortgageInterestCeiling` (read from the CLI's opening words, never tax-core's "Home-loan interest ceiling, baht."). A plan with no profile is not asked, and a refusal is kept as the read's own error, so the page shows nothing false. The tax profile page lists the notes under the claims, one paragraph each, as plain text. A note can state an amount (the shared home-loan interest, for one), so Hide amounts hides them and says so (see the amendment below). The first decision above ("No new read") still holds for the profile itself, which `scenario show` carries.

The Demo's other reads are byte-identical; its only new leaf is the notes read. Its `base` plan gained an income Flow without a tax label after its Levy was written, so its dry run is refused and its leaf holds that refusal. `scripts/tax-notes-cli.test.ts` runs the real binary for the separate-loans note, a shared-interest sentence, a kept-claims sentence, a departed-id sentence and a no-taxed-income sentence, so rewording one of those CLI sentences fails it.

## Amendment (2026-11-26): Hide amounts covers the cards, the claims table and the notes (#636)

- **The cards.** Every amount a card shows reads through the shared mask (`MaskedAmount`, which uses `maskMoney`): the digits become `•••••`, the currency and any words after them ("kept, not claimed by this Return") stay, and a screen reader hears "amount hidden". A count (children, parents, relatives with a disability) is not money, so it stays a digit, as a rate is not money on the Tax page (ADR 0024).
- **The claims table.** Every money cell of "Who claims each allowance" and the stored shared home-loan interest under it read through the same mask; a count and "None" stay as they are. `claims.ts` keeps each amount's digits beside its text (`ShownAmount`), so the page masks the digits and never the words around them.
- **The notes.** A CLI note can state an amount (the sentence about shared home-loan interest names it), so with Hide amounts on the section shows one line, "The notes on the stored claims are hidden with the amounts.", instead of the sentences.
- **The drawer's warning.** When a whole save would drop a stored shared home-loan interest, its sentence reads through the same mask (`TaxDropWarning`, which uses `MaskedAmount`): the words before and after the amount stay, the digits become `•••••`, " THB" stays, and a screen reader hears "amount hidden".
- **What does not change.** The per-year table already reads `Money`, so it needs no change. The profile form's fields show the person's own input, so they stay unmasked. A locked amount field takes no input, so its value is masked; a locked count stays shown. With Hide amounts off the page shows the same text and markup apart from the comment markers Svelte writes for a block.

## Amendment (2026-11-26): the flat claims wait after a holder swap

A separate filing whose household swapped holder and partner after its tax was written still records the earlier holder as `claimsHolder` ([cli ADR 0075](../../../cli/docs/adr/0075-a-two-earner-plan-states-its-filing-choice-and-scenario-tax-writes-one-levy-per-return.md)), so its flat keys are that person's claims while a bare value names the new holder. The page no longer offers a control that would send one.

- **The lock.** While `flatClaimant` names someone (`src/lib/view/tax-settings/flat-claims.ts`), every control that sends a bare value for a flat claim is disabled: a card whose every row is a flat claim (Family, Insurance, Giving, Social security), every flat field in the drawer, the "Not in your plan yet" buttons for those classes, and the "State the whole profile instead" switch, whose save would send the flat values the form shows. The Home card keeps its Edit while `canClaimShared` offers the shared field, because the shared home-loan interest is sent as `shared=`; with no partner or no Owners the drawer would show only a disabled field, so the card waits too. The filing status keeps its Edit because a status is not a claim, and the drawer's shared field stays writable. A bare merge on such a plan already moves the claims to each Return, so a shared-only save is safe; the disabled fields are the ones the person cannot check.
- **Why, once.** One sentence above the cards, repeated at the top of a locked drawer, in the household's words for the recorded person ("your partner", or "the earlier holder" for an id it no longer names), names `traj scenario tax <plan> --from-stored` in code. That command moves the claims to each Return, and the page is editable again. When the recorded person has left the household, the sentence says instead that those claims stay unclaimed until they are stated for a person who has a Return.
- **No id becomes a name.** The recorded holder's column in "Who claims each allowance" takes the same words, so a departed id reads "The earlier holder" and never `me`. The CLI's note about a departed id still quotes that id, and the CLI writes it for every id the household no longer names, so the page rewrites it by recognising its opening words (`notes.ts`): "the earlier holder" when the id is the recorded `claimsHolder`, and "another person" for any other, such as a renamed partner. The "Not in your plan yet" buttons take the claimant's words too, so a flat class never says "you" of that person's claims. The claims table's row labels are neutral ("Parents supported", "Health insurance premiums"), because each column is one person's Return; the cards keep the claimant's words. A column whose id the household no longer names, other than the recorded holder, reads "Another person"; with no household at all the columns show their ids, as every person does then.
- **A tab read before the swap.** `scenario household` leaves `contentHash` unchanged (cli ADR 0055), so a tab opened before a swap still names the hash it read. Before the edit server runs a `merge-tax` or a whole tax save that carries a flat claim, it reads `scenario show <plan> --json` again, a read leaf, and refuses while `flatClaimant` names someone there, with the plan's `traj scenario tax <plan> --from-stored` command in the sentence; nothing is written.
- **Unchanged.** A joint or single filing, a separate filing whose recorded holder is still the household's holder, and a plan with no household keep every control and every word. The Demo's plans record their own holder, so no control there waits and its Snapshot is unchanged.

`scripts/tax-swap.test.ts` runs the real binary: it swaps the household, checks through the page's own view models and components that every control left enabled sends only the status or `shared=`, refuses a stale tab's flat merge, runs `--from-stored` and sees every control back and a bare edit write the new holder, then swaps again and sends the shared interest and a filing status through the real edit path. `tax-swap.svelte.test.ts` pins the swapped page, and `browser/tax-swap.e2e.ts` checks it at 360 px against the editable scratch Dashboard.
