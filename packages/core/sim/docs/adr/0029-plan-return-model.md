# A Return model built from the plan: one market factor, a committed integer quantile table

Status: accepted

ADR 0011 ships chance of success with no Return model of its own: the caller hand-writes a joint bucket
table, which no one outside the project will do (#411). Most planners describe market risk with two numbers
per holding, an expected yearly return and how much it swings. The plan already states the first, as an
Account's `rate`. This ADR adds the second, `volatility`, and `planReturnModel`, which turns both into the
bucket table ADR 0011 already takes. It adds no growth rule, no new engine path and no change to a
hand-written model file.

## Decision

- **The field.** An asset Account may carry `volatility` (0 to 10000 bps, `RATE_OUT_OF_RANGE` outside it): the
  standard deviation of its yearly return. A liability may not (`LIABILITY_MISUSE`). It is an optional,
  additive field, so `Scenario.schemaVersion` stays 4 (precedent: ADR 0026 to 0028). `project()`, FI and every
  deterministic figure ignore it; only `planReturnModel` reads it.
- **The builder.** `planReturnModel(scenario, { buckets })` returns `{ ok: true, model, notes }` or
  `{ ok: false, problems }`. `buckets` is a power of two from 16 to 1024 (`INVALID_BUCKETS`), so each bucket
  weighs exactly `2^32 / buckets` and the weights total 2^32 with no remainder. The model's id is
  `plan-<buckets>`. The same Scenario and `buckets` give a byte-identical model. The Scenario must pass
  `check()`.
- **Who is in the model.** Every asset Account with a `volatility` above 0, in Scenario order. Any other
  Account is left out, so it keeps its own `rate`, compounding and accrual exactly. Putting it in with a
  constant return would round its month return to a whole basis point (a 7 per cent rate would become 7.06),
  which would move a figure the user never made uncertain.
- **One market factor.** Bucket `b` carries one standard normal value `z_b`. Every volatile Account moves
  with it: its span return in bucket `b` is `m + z_b x s`, with `m` the month return equivalent to its
  yearly `rate` and `s` its yearly volatility scaled to a month. The Accounts are fully correlated. That is
  the conservative case for a stock-heavy plan, needs no matrix and is easy to say; a per-Account correlation
  can be added later as a new field. Months are independent, because the engine draws each month's bucket
  from the seed on its own (ADR 0011).
- **Normal, not lognormal.** The month span return is normal, which the bucket table states directly. The
  expected value of a year's compounded growth is then `(1 + m)^12`, the stated rate, within 1 bp, for the
  table and for a row with no change to the Account in the middle of it. The median is lower by about
  `volatility^2 / 2`, as for any volatile return.
- **A mid-row change is neutral.** The engine used to restart a row's linear walk from a mid-row deposit,
  withdrawal or payout, so the row's factor was `1 + r + r²·h₁h₂/D²`, which with volatility (`E[r²] ≈ s²`) is not
  small. Measured for a fund at 7% and 15% volatility from the built model (256 buckets) before the fix: 700.02
  bps a year with no mid-month change, 738.8 with a change on the 25th of 30, 760.7 with a change mid-month, 791.2
  with four weekly changes. Issue #432 fixed it ([ADR 0005](0005-seeded-monte-carlo-seams.md), "A change inside a
  row is neutral"): the row's start balance takes the full `1 + r`, an amount added or taken mid-row takes
  `1 + r·h₂/D`, and the figure is now 700.02 bps for every one of those cases. This unblocks `traj dashboard`
  defaulting to this model (#412).
- **A Timeline that starts or ends mid-month.** Its first row used to get a full month's return over a part
  month: about +30 bps in year one, and the last row had the same flaw. Each Market row now carries `span`, the
  counted days of its whole month, so a part row takes its share of the return (ADR 0005, "A row cut by the
  Timeline"). It is exact, not rounded to a basis point.
- **The quantile table.** `z_b` is the standard normal quantile at the midpoint `(b + 1/2) / buckets` of
  bucket `b`, stored as an integer in millionths in `src/market/normal-table.ts` for the seven sizes. The
  table is odd-symmetric, so only the upper half is stored and the sum is exactly 0, which makes the weighted
  mean of `z` exactly 0. The file is generated by `bun run normal-table:update`, which imports
  `src/golden/oracle-normal.ts` (pi by Machin's formula, exp and the cdf by series, the quantile by bisection,
  all BigInt fixed point at 10^40). The table is generated from and pinned to that oracle, not checked against
  an independent source: a test re-derives every table from the oracle, pins each table, and checks no value
  sits within 100 trillionths of a rounding boundary. So that test proves only that the file was not
  hand-edited. The outside check, run once with Python's `statistics.NormalDist().inv_cdf`, gives identical
  millionths for all seven sizes (1,016 values, 0 mismatches).
- **The month return.** `m` solves `(1 + m)^12 = 1 + rate` by integer bisection in BigInt, in millionths of a
  basis point, floored. A nominal Account (`compounding`) first becomes its effective yearly factor
  `(1 + rate / n)^n` as an exact fraction. A month cannot more than double: a root above +100 per cent
  saturates there. `s = volatility / sqrt(12)` is an integer square root in the same unit, rounded half up. A
  yearly standard deviation splits into twelve independent months by the square root of twelve.
- **Whole basis points.** A model states whole bps. `m + z x s` is exact in integers (units of 10^-12 bp) and
  is rounded by largest remainder, not each value on its own: every value is floored, and the surplus bps
  go to the largest remainders, the lower index first on a tie, until the sum is the exact total rounded half
  up. So the weighted mean of the month return is within half a bp over `buckets` of `m`, which compounds to
  the stated rate within one basis point for every size, for the table itself (rounding each bucket alone left up to 2 bps at 16
  buckets). A value is never more than 1 bp from its exact one, and two Accounts' columns can differ from
  strict co-movement by that rounding.
- **A floor and a ceiling.** `checkReturnModel` accepts a span return from -9999 to 10000 bps, so a value
  outside it is clamped to that range, and `notes` lists `{ account, clamped }` for each Account that had
  any. An Account cannot fall below zero. (The issue named -10000; the model's own check refuses it.)
- **Integers only.** Every number that reaches a figure is a BigInt or a safe integer: the table, the root,
  the volatility, the rounding. No `Math.random`, no float, no clock.
- **The spread of the table.** Equal-probability midpoints put no mass in the tails, so a table's variance is
  slightly under 1: within `1.4 / buckets` below it (0.924 at 16, 0.9987 at 1024). A path's volatility is
  understated by that factor's square root, about 4 per cent at 16 buckets and 0.07 per cent at 1024. The
  CLI's default of 256 buckets is 0.3 per cent. The quantile table is not rescaled, because the table the
  issue names is the quantiles themselves.
- **Inflation stays fixed.** A Return model is per Account, and the Scenario's inflation drives Flow growth
  and the real view, not an Account's return. Letting inflation vary per path is a later decision, so a path's
  inflation is the Scenario's. [ADR 0033](0033-inflation-is-drawn-per-market-path-from-an-inflation-factor.md)
  amends this bullet: a plan that states `economy.inflationVolatility` draws one yearly rate per Market path
  from the model's `inflation` factor, so a path's inflation is its own Price path. Absent or 0, this bullet
  holds exactly as written, and no extra word is drawn.
- **The check.** `INVALID_BUCKETS` is new in `ERROR_CODES`. `checkReturnModel` now allows up to 1024 buckets
  (it capped them at 512), so a built model passes it. The raised cap also applies to the FI probability
  method (ADR 0005), which runs the same check. The CLI refuses it at `--buckets`.

## Considered options

- **A seeded normal sampler (Box-Muller, a sum of uniforms).** Rejected: a bucket table is what ADR 0011
  already draws from, and a table is inspectable, saveable and the same under every engine. A sampler would
  add a second source of draws and an integer `ln`, `sqrt` and `cos` for no gain at these bucket counts.
- **Rounding each bucket half up.** Rejected for the one-basis-point mean bound above.
- **Putting a zero-volatility Account in the model at its rate.** Rejected: see "Who is in the model".
- **Lognormal.** Rejected: it needs `exp` in integers, and a normal month with the floor stays sane.
- **A correlation matrix.** Left for a later field.

## Consequences

- `parity/cases.json` records one `freelancer-plan-chance` case, which hashes the built model and the chance
  run over it under Bun and Node. The model hash is unchanged; #432 moved the chance hash (ADR 0005).
- A plan with no volatile Account builds a model with no Accounts, so every path is identical. The caller
  decides what to say (the CLI refuses it).
